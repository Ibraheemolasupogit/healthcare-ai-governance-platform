# 0005. Policy-as-code and evidence-as-code principles

**Status:** Accepted

## Context

Governance controls and audit evidence that live only as prose in a wiki or a spreadsheet drift
from what the system actually enforces and cannot be tested, versioned, or reviewed the way code
can. A platform that claims to govern AI use in healthcare research should hold itself to the same
standard: controls should be expressed in a form that can be reviewed in a pull request, tested in
CI, and executed deterministically, and the evidence that a control was satisfied should be
generated as a reproducible artifact rather than written by hand after the fact.

## Decision

Two principles govern how later milestones implement the governance and audit/evidence planes:

- **Policy-as-code:** governance controls (what counts as an approved dataset, an allowable
  access grant, a compliant model) are expressed as versioned, reviewable, testable code or
  declarative configuration living in the governance control plane
  (`src/governance_platform/` and `governance/`), not as free-text policy documents that the
  platform doesn't actually enforce. Where `governance/*.md` documents describe a control today,
  they describe *intent* to be encoded this way in a later milestone, not an implemented policy
  engine.
- **Evidence-as-code:** audit and compliance evidence (that a control was checked, that an access
  review happened, that a risk score was computed) is generated by running code against recorded
  data and emitting reproducible artifacts, rather than manually assembled. This governs the
  future design of the audit/evidence plane and `outputs/`.

Milestone 1 does not implement either principle — no policy engine and no evidence generator
exist yet. This ADR fixes the design direction for when those planes are built.

## Consequences

- Future controls and evidence artifacts will be diffable, reviewable, and testable like any other
  code, which is a stronger integrity guarantee than hand-maintained documents but requires more
  upfront engineering than a spreadsheet-based approach.
- `governance/*.md` documents must be read as operating-model intent, not as a description of an
  enforced policy engine, until a milestone explicitly implements enforcement — README and ADR
  language elsewhere in this repository is written to keep that distinction visible.
- This constrains later milestones' technology choices toward things that can run in CI (e.g. a
  rules engine or declarative policy files checked by tests) rather than external, unversioned
  policy tools.
